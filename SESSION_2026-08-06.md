### 2.2 Blocker — disk full broke docker

The first attempt to query the DB failed with a docker overlay2
`input/output error`:

```
Error response from daemon: open /var/lib/docker/overlay2/.../lower: input/output error
```

Diagnosis:

- Disk was at **99% capacity, ~3.1 GiB free** (`/System/Volumes/Data`).
- The cause: the earlier `docker compose up -d --build backend` had been
  downloading multi-GB torch/CUDA layers and filled the disk.
- The build process had died (no longer running).

Fix — prune docker's dead weight:

```bash
docker builder prune -af   # freed 28.57 GB of build cache
docker image prune -af     # freed 12.87 GB of unused images
```

Disk after: **~21 GiB free**. Docker worked again.

Because of the orphan ambiguity, I asked the user to choose the scope. They

### 2.4 Deletion execution

Transaction 1 (delete sources + orphan `bajra` by explicit id + any entity
linked to bajra versions):

```sql
BEGIN;
DELETE FROM knowledge_source WHERE external_reference_id ILIKE '%bajratechnologies.com%';
DELETE FROM entity
WHERE id = 'da7e84b2-...'                    -- orphan 'bajra' duplicate
   OR id IN (SELECT ... entities linked to bajra versions ...);
COMMIT;
```

Result: `DELETE 2` sources, `DELETE 1` entity (only the orphan `bajra`).
Counts went 78 → 77 entities, 61 → 52 relations (cascaded 9 `employs`), 67
values, 103 → 93 chunks.

**Ordering bug caught & fixed:** the second `DELETE` only removed 1 entity.
Because the sources were deleted *first*, the cascade already removed the bajra
versions' chunks/maps, so the subquery "entities linked to bajra versions"
found nothing by the time it ran. The 4 bajra-only entities survived.

Transaction 2 (delete the remaining bajra-only entities by id):


Result: `DELETE 5`, cascading 7 relations (e.g. `Bajra Technologies founded_by

## 3. Verification rabbit hole — the "flapping" data

During verification the `/graph/path` for `Ashok Maharjan → Alpinist Studios →
Atishaya Maharjan` returned `null`, and repeated queries showed the
`Alpinist Studios employs Ashok Maharjan` relation **appearing and
disappearing** between consecutive queries while the total relation count
stayed pinned at 45.

### 3.1 What was investigated and ruled out

- **Not a bug in `find_path`**: the recursive CTE walks undirected edges and is
  correct; when the relation is absent, no path exists.
- **Not my deletion**: my deletes only touched bajra entities/relations. The
  `employs Ashok Maharjan` relation is Alpinist → Alpinist and was never in my
  `DELETE` list. Math confirmed: 45 = 61 − 9 − 7.
- **Not a second database**: checked the homebrew postgres theory. The API's
  env is `POSTGRES_HOST=localhost POSTGRES_PORT=5433` (`db/session.py` builds
  the URL from env) → the API reads the **same** docker postgres I was
  querying. One DB.
- **Not cron/launchd**: no crontab, no launch agents touching the project.
- **Not the backend docker container**: enabled
  `log_statement='all'` + `log_connections='on'` in postgres and watched.
  The backend container (host `172.18.0.4`) connects roughly once a minute and
  only runs an **alembic version probe**
  (`SELECT alembic_version.version_num`) then `COMMIT` — a no-op, because the
  DB is at `0003` and the migration files are mounted from the clean host chain
  (`docker-compose.yml` mounts `./backend/alembic/versions`). **No DML.**
- **No concurrent connection**: `pg_stat_activity` showed only the API's idle
  pool connection.

### 3.2 Root cause

The **local ingestion worker** (`run_worker.py`) had been running and
re-ingesting alpinist sources; during re-ingestion it deletes and re-creates a
source's EAV rows. It was mid-churn during my cleanup/verification, which is
why the relation toggled on/off. Once the worker exited, the data stabilized.

- Confirmed stable: 8 consecutive polls returned the same value, and the
  postgres log showed **zero writes** over a 3+ minute window.
- Reverted the diagnostic logging (`log_statement`/`log_connections` back to
  `none`/`off`).

### 3.3 Current graph behavior

In the now-stable state the `employs Ashok Maharjan` edge is not present (the
worker's final re-ingest left it out). This is a data-quality artifact of the
incomplete/duplicate-prone ingestion — **not** a regression from the cleanup.
The graph API itself is healthy: search, neighbors, and paths all work for the
relations that exist.

Known ingestion caveats (pre-existing, documented in
`KNOWLEDGE_GRAPH_README.md`): duplicate entities (e.g. `Alpinist`,

## 5. Rebuilding the backend docker image

### 5.1 Why

- The running `ai-customer-assistant-backend` container was built from an old
  image (before the `--app-dir` fix in `scripts/entrypoint.sh`), so its
  `uvicorn main:app` resolved the placeholder `backend/main.py` and crashed →
  `Restarting` loop.
- Rebuilding produces a new image with the fixed entrypoint so the dockerized
  API serves on port 8000.

### 5.2 What the build does (`backend/Dockerfile`)

1. Base `python:3.12-slim`; installs `postgresql-client` (for `pg_isready`)
   and `curl`.
2. Copies the `uv` binary (0.11.20) from a ghcr.io image.
3. `uv sync --no-install-project` — installs all dependencies from
   `pyproject.toml` / `uv.lock` (this is the slow, multi-GB part: torch, CUDA
   wheels, scikit-learn, etc.).
4. Copies source; `uv sync` again to install the project itself.
5. Sets `PYTHONPATH` so `main:app` resolves to
   `src/ai_customer_assistant/main.py`; `chmod +x scripts/entrypoint.sh`.

On container start, `scripts/entrypoint.sh`: wait for postgres →
`alembic upgrade head` (no-op at `0003`) → `uvicorn main:app --app-dir
/app/src/ai_customer_assistant --host 0.0.0.0 --port 8000`.

### 5.3 Execution & monitoring

```bash
nohup docker compose up -d --build backend > /tmp/backend_build.log 2>&1 &
```

Monitored `/tmp/backend_build.log`:
- Wheel downloads (`pydantic-core`, `networkx`, `nvidia-*`, `triton`, etc.).
- `uv sync` install phase (`+ torch`, `+ scikit-learn`, ...).
- Image export — disk briefly dropped to **~8 GiB free** (96%), then the
  export completed.
- `Container ai-customer-assistant-backend Started`.
